# Account profiles, username sign-in, avatars and deletion

Email/password, Google and GitHub remain Firebase Authentication identities. Signup adds a full name, mobile number, unique case-insensitive username, password and confirmation. Mobile numbers are profile data; there is no SMS verification or phone-number authentication. Existing accounts can add a username in Settings.

SQLite `account_profiles` links a unique username, full name, mobile and avatar index (0–6) to the existing verified owner key. Foreign keys cascade on account deletion. No password or Firebase token is stored. Profile reads/updates use the server's existing verified Firebase identity. Guests cannot claim usernames or save account avatars.

`POST /api/auth/username-login` validates username/password against Firebase before returning the mapped email to the caller. The browser then establishes its normal Firebase SDK session. Unknown usernames and wrong passwords have the same response. Persistent hashed IP/username buckets limit attempts over a 15-minute window. This endpoint accepts passwords transiently; production must use HTTPS, and request bodies must not be logged by any proxy or middleware. There is no public username-to-email lookup.

`DELETE /api/user/account` requires a verified Firebase token, an `auth_time` within five minutes and the exact confirmation `DELETE`. Settings first reauthenticates with the password or Google/GitHub popup. Firebase's [user management guidance](https://firebase.google.com/docs/auth/web/manage-users) describes recent-login requirements, and its [REST API](https://firebase.google.com/docs/reference/rest/auth#section-delete-account) supplies account deletion. The server deletes the Firebase account and commits removal of the local owner/profile/history. A rejected Firebase deletion leaves local data intact; local removal is committed only after Firebase confirms deletion. Cross-service deletion is not a distributed atomic transaction: a network timeout or server/database failure around remote completion can require administrator reconciliation. Exported copies are outside this deletion's scope.

Six generated character portraits are self-hosted in `assets/ai-avatars.png`. CSS selects a portrait from the sheet; the database stores only the selected index, never an arbitrary URL. There is no external avatar request or user-uploaded-image handling.

Validation: temporary-database ownership, uniqueness, rate limits, wrong-password responses, recent-login rejection, failed-deletion rollback and successful cleanup; mocked Firebase client signup/sign-in/security actions and avatar selection. No live personal account was created, edited or deleted during testing. Configure Firebase email/password, Google and GitHub providers as described in `SIGNIN_SETUP.md`.
